# TEST 61 — REDZED COLLECTION SHARED GROUP CROSS-EFFECT RULES

Status: LOCKED IMPLEMENTATION CONTRACT — 2026-09-01
Scope: TEST61 only. MAIN G and solved TEST60 media/thumbnail/delete mapping remain untouched.

121. REDZED COLLECTION is the group conversation. Do not create a second artificial Group identity. One permanent Party/Customer chat is shared by the customer and the applicable REDZED staff members already mapped to that chat.
122. Any human GROUP message is a group event. The sender is excluded from notification recipients; every other active group member is an intended recipient. Customer -> all applicable staff. Staff -> customer + all other applicable staff. No hardcoded customer/staff IDs.
123. Notification, unread, delivery and read state are member-specific. Reading on one member/device must not clear another member's unread state.
124. Message receipt semantics: single tick = accepted/sent but not yet delivered to every intended member; double tick = delivered to every intended member; blue double tick = read by every intended member. Delivery/read must be based on member acknowledgements, not merely on push-provider acceptance.
125. Unread badge for staff/customer is calculated for that signed-in member. Conversation-list/app badge counts unread conversations/customers, not raw message count. Multiple unread messages from one customer conversation count as one unread conversation.
126. Notification tap must deep-link/focus the exact permanent customer REDZED COLLECTION conversation. Push payload must not expose stale/deleted message text after a global delete.
127. Collection, More Samples, Requirement, PI and CI are not parallel chat copies. They remain the existing authoritative commercial lifecycle and are projected into the same REDZED COLLECTION group as one living business card/state. Source IDs remain the existing Collection/Requirement/PI/CI IDs.
128. Existing lifecycle remains authoritative: Collection -> updates -> Requirement -> PI -> CI -> terminal close. PI generation closes/converges the linked Requirement according to locked Rule 49; it does not create an unrelated staff-side Requirement state. Customer and staff views must resolve the same source state.
129. Customer More Samples / Requirement changes must cross-effect the staff group actionable state using the existing shared Collection update sequence and pending/cutoff rules. Staff processing/PI state must cross-effect the customer view from the same authoritative records. Do not duplicate business records merely to display chat activity.
130. Normal human message deletion has two modes: DELETE FOR MYSELF and DELETE FOR ALL. DELETE FOR MYSELF is member-specific visibility only and never removes the message for other members.
131. DELETE FOR ALL is sender-controlled for that sender's own normal human message only while no other intended group member has read it. As soon as any other member has read the message, DELETE FOR ALL is blocked and only DELETE FOR MYSELF remains for the sender.
132. Customer cannot DELETE FOR ALL a company/staff-authored message. Staff cannot ordinarily DELETE FOR ALL another member's message. Customer can DELETE FOR ALL the customer's own eligible unread message; staff can DELETE FOR ALL the staff member's own eligible unread message.
133. DELETE FOR ALL must be a server-authoritative tombstone/global-redaction state, not an unsafe physical hard-delete. Audit identity/timestamps remain; visible content and future notification preview are removed/replaced for all members.
134. Collection/Requirement business objects use controlled business deletion, not normal message Delete For All. While Collection/Requirement is OPEN/active, deletion is locked for both customer and staff.
135. After Collection/Requirement leaves OPEN/active state, deletion may be offered only when the existing lifecycle/dependency rules declare it eligible. It requires an explicit warning/confirmation and authorized action. Active PI/CI or other blocking dependency prevents deletion. Audit/history remains.
136. Business deletion must cross-effect both customer and staff views because both reference the same source object. It must never leave one side showing an active object that the authoritative lifecycle considers deleted/closed.
137. Technical lifecycle events remain backend audit/history and must not spam duplicate ordinary chat bubbles. The approved one-living-Collection-card rule remains intact.
138. Push delivery must follow the real group-member mapping. Existing customer-only TEST61 push enqueue is transitional and must not be treated as final group semantics until sender-excluded all-member recipient routing is implemented and runtime-verified.
139. TEST61 implementation must preserve MAIN G stable customer media/thumbnail behavior and the existing Collection/Requirement/PI/CI business rules. Add member receipt/delete/cross-effect state surgically; do not rewrite solved stock, PI, CI, pricing or collection-number logic.
140. TEST61 is PASS only after runtime verification of: customer->staff push; staff->customer+other-staff push; sender exclusion; exact-chat deep link; per-member unread; all-member delivery/read ticks; Delete For Myself; eligible Delete For All; read-lock on Delete For All; OPEN Collection/Requirement delete lock; eligible closed-state warning delete; and Collection/Requirement/PI cross-effects on both customer and staff views.
